# Live Vehicle Tracking & On-Field Reporting Architecture

This document technically explains the actual implementation of live vehicle tracking and on-field reports collection within the ManipurRoadRisk codebase.

## Section A — Live Vehicle Tracking

### 1. Data Source
Live vehicle data is **simulated** in the backend API. There are no actual GPS devices, mobile apps, or IoT devices transmitting live data to this system. The data originates from a hardcoded Python list (`VEHICLE_DATA`) in `frontend/api/app.py`.

### 2. Location Data Flow
The location data follows a simulated pipeline:

Mocked Vehicle Data (`app.py`)
    ↓
Time-based interpolation (simulated movement)
    ↓
Flask REST API Endpoint (`/api/vehicles`)
    ↓
Frontend JS Polling (`fetchAPI("/vehicles")`)
    ↓
Leaflet GIS Map
    ↓
Live Vehicle Marker (`L.marker`)

### 3. Communication Technology
The project uses **HTTP Polling** for vehicle tracking.
- The frontend JavaScript uses `setInterval(updateVehicles, 5000)` in `app.js` to hit the `/api/vehicles` REST endpoint every 5 seconds.
- SSE (Server-Sent Events) is used for Alerts (`/api/stream/alerts`), but *not* for vehicle tracking.

### 4. Map Visualization
- **Mapping Library**: Leaflet.js
- **Map Tile Provider**: OpenStreetMap (OSM) public tiles (`https://{s}.tile.openstreetmap.org/{z}/{x}/{y}.png`).
- **Vehicle Markers**: Coordinates are received as `[lat, lon]`. The application renders them using `L.marker()` with a custom HTML `divIcon`.
- **Marker Updates**: If the marker for a specific vehicle ID already exists in the `vehicleMapMarkers` dictionary, its location is updated via `marker.setLatLng()`.
- **Route/Road Geometry**: Roads are rendered as `L.polyline` instances on the map.

### 5. Real-Time Update Flow
```text
Frontend interval ticks (every 5s)
        ↓
Frontend calls GET /api/vehicles
        ↓
Backend computes simulated coordinates based on current timestamp
        ↓
Backend responds with JSON vehicle list
        ↓
Frontend parses JSON
        ↓
Update existing vehicle marker coordinates via Leaflet setLatLng()
        ↓
Map re-renders vehicle position
```

## Section B — On-Field Report Collection

The on-field reporting collection system is a mocked interface meant to demonstrate how the UI would look.

- **Field reporter interface**: A web-based modal form (`#report-modal` in `index.html`).
- **GPS coordinates**: Handled by the browser's `navigator.geolocation` API when the user clicks the GPS button.
- **Road/segment identification**: A static dropdown populated from the dashboard's road segment list.
- **Report categories**: Static dropdown (Landslide, Flood, Road Damage, Bridge Damage, Debris, Accident).
- **Road condition/severity**: Static dropdown (Low, Medium, High, Critical).
- **Images/Videos**: «Not currently implemented.»
- **Text description**: Simple textarea input.
- **Timestamp**: Generated by the backend upon receipt.
- **Backend API**: Data is posted to `POST /api/field-reports`.
- **Database/Storage**: «Not currently implemented.» The backend immediately discards the data and responds with a simulated success and a random Report ID.

### Actual Architecture:
```text
Web Reporting Interface (Modal)
      ↓
User Input + Browser Geolocation
      ↓
POST to Flask API (/api/field-reports)
      ↓
Mocked Success Response
      ↓
Data Discarded (No DB Storage)
```

## Section C — Report Processing

Because there is no database or persistent storage, there is **no actual report processing**.

- When the frontend calls `GET /api/field-reports` to list reports, the backend API generates a list of 10 completely random reports on-the-fly using a static Python seed.
- Validations, road segment matching, and ML classification are **not currently implemented** for field reports.
- Dashboard updates happen simply by fetching this randomized data and re-rendering the HTML list and map markers.

## Section D — Technology Stack

| Layer | Technology | Purpose |
| --- | --- | --- |
| **Frontend** | Vanilla JS + HTML/CSS | User interface, routing (`app.js`) |
| **GIS** | Leaflet.js | Map rendering and markers |
| **Map Data** | OpenStreetMap (OSM) | Base map tiles |
| **Routing** | OSRM (via `routing.py`) | Fetching real road geometries for routes |
| **Backend** | Python Flask | REST API and static file server |
| **Database** | None (Mocked Data) | «Not currently implemented.» |
| **Real-time** | Polling & SSE | Polling for vehicles; SSE for alerts |
| **Storage** | None | «Not currently implemented.» |
| **Authentication** | None | «Not currently implemented.» |
| **ML** | Scikit-Learn | Risk prediction (`predict.py`) |

## Section E — Security & Reliability

The application currently functions as a prototype/dashboard frontend and lacks production security mechanisms.

- **API authentication**: «Not currently implemented.»
- **Authorization**: «Not currently implemented.»
- **Input validation**: Basic client-side JavaScript validation (e.g. checking empty fields).
- **GPS data validation**: «Not currently implemented.»
- **File upload validation**: «Not currently implemented.» (Uploads not supported)
- **Rate limiting**: «Not currently implemented.»
- **Error handling**: Basic `try/catch` in JavaScript, failing gracefully with toast notifications.
- **Database security**: «Not currently implemented.»
- **HTTPS**: «Not currently implemented.» (Runs on localhost HTTP).
- **Sensitive data protection**: «Not currently implemented.»
